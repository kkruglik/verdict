# Session: Unit Consistency, Silent Constraint Bugs & Integration Test Harness

## 1. Initial Goal
Two related goals discovered during review of the existing parquet loading code:
1. Fix unit inconsistencies in `TimeColumn` and `DateTimeColumn` — the canonical storage unit was wrong or inconsistent between CSV and parquet paths
2. Build an integration test harness using parquet fixtures to catch silent failures in date/time/datetime constraint checks

---

## 2. DateTimeColumn Unit Inconsistency

### Attempt
Parquet loader stored both `TimestampMillis` and `TimestampMicros` as-is into `Vec<Option<i64>>`:
```rust
(ColBuilder::DateTime(v), Field::TimestampMillis(val)) => v.push(Some(*val)),
(ColBuilder::DateTime(v), Field::TimestampMicros(val)) => v.push(Some(*val)),
```

### Issue
The canonical unit was determined by looking at `naive_datetime_to_i64`:
```rust
pub fn naive_datetime_to_i64(naive_datetime: &NaiveDateTime) -> i64 {
    naive_datetime.and_utc().timestamp_micros()
}
```
Canonical unit is **microseconds**. `TimestampMicros` was correct. But `TimestampMillis` stored raw milliseconds — off by 1000x from what the rest of the code expected. Constraints like `After`/`Before` on a parquet file using millisecond timestamps would compare against the wrong scale and either always pass or always fail.

### Fix
Normalize `TimestampMillis` to microseconds at load time:
```rust
(ColBuilder::DateTime(v), Field::TimestampMillis(val)) => v.push(Some(*val * 1000)),
(ColBuilder::DateTime(v), Field::TimestampMicros(val)) => v.push(Some(*val)),
```
`TimestampMicros` is already in the right unit, stored as-is. `TimestampMillis` multiplied by 1000. Converting millis → micros is lossless (no precision lost).

## 3. TimeColumn: Wrong Canonical Unit

### Attempt
`TimeColumn` stored `i32` (milliseconds since midnight, matching parquet's `TimeMillis`). Conversion function:
```rust
pub fn naive_time_to_i32(naive_time: &NaiveTime) -> i32 {
    naive_time.num_seconds_from_midnight() as i32
}
```

### Issue
`num_seconds_from_midnight()` returns **seconds**, not milliseconds. The stored values and constraint thresholds both went through this function, so for the CSV-only path everything was internally consistent. But parquet `TimeMillis` stores raw milliseconds — storing those in a column whose comparison functions expect seconds produced wrong results.

The deeper problem: seconds was the wrong unit to pick in the first place. Parquet `TimeMicros` provides microsecond precision. Storing microseconds as seconds throws away sub-second precision entirely.

### Why i32 can't hold microseconds
Max microseconds in a day: `86_400 * 1_000_000 = 86_400_000_000`. `i32::MAX` is `2_147_483_647`. Doesn't fit. So the storage type had to change from `i32` to `i64`.

### Fix
Changed `TimeColumn` to `Vec<Option<i64>>`. New conversion functions:
```rust
pub fn naive_time_to_i64(naive_time: &NaiveTime) -> i64 {
    let midnight = NaiveTime::from_hms_opt(0, 0, 0).unwrap();
    (*naive_time - midnight).num_microseconds().unwrap()
}

pub fn i64_to_naive_time(v: i64) -> Option<NaiveTime> {
    let secs = v / 1_000_000;
    let nanos = (v % 1_000_000) * 1000;
    NaiveTime::from_num_seconds_from_midnight_opt(secs as u32, nanos as u32)
}
```

`num_microseconds()` returns `Option<i64>` because a large duration could overflow — but for time-of-day (max 24h) it never will, so `unwrap()` is safe.

`i64_to_naive_time` splits microseconds into seconds + nanoseconds because `from_num_seconds_from_midnight_opt` is the available API. Microseconds leftover (`v % 1_000_000`) converted to nanoseconds by multiplying by 1000 (1 microsecond = 1000 nanoseconds).

Parquet arms updated:
```rust
(ColBuilder::Time(v), Field::TimeMicros(val)) => v.push(Some(*val)),
(ColBuilder::Time(v), Field::TimeMillis(val)) => v.push(Some(*val as i64 * 1000)),
```

### Trap: i32 overflow before cast
First attempt was `(*val * 1000) as i64`. `*val` is `i32`. `86_399_999 * 1000` overflows `i32` before the cast happens. Fix: cast first, then multiply: `*val as i64 * 1000`.

## 4. Integration Test Harness Design

### Goal
Verify that every date/time/datetime constraint actually catches violations — not just that it passes on valid data.

### Discovery that motivated this
Running tests manually revealed that some constraints "passed" on data that clearly violated them. Without systematic failing cases, silent bugs were invisible.

### Structure
Three fixture folders generated by Python scripts:
- `fixtures/time_checks/` — `time32("ms")` and `time64("us")` columns
- `fixtures/date_checks/` — `date32` columns
- `fixtures/datetime_checks/` — `timestamp("ms")` and `timestamp("us")` columns

Each folder contains:
- `data.parquet` — generated parquet with both pass and fail columns
- `schema.json` — constraints matching each column
- `expected.json` — flat list of `{column, constraint, passed}` authored in the same Python script that generates the data

Pass columns: data satisfies the constraint, expected `true`.
Fail columns: data deliberately violates the constraint, expected `false`.

`scripts/compare_results.py` runs the CLI, parses JSON output, compares actual vs expected per rule, prints `OK` / `WRONG` / `MISSING` per entry.

### Why generate expected.json from the same script
The Python script that generates the parquet data knows exactly what values each column contains and what constraints are applied. Deriving `expected.json` there eliminates the possibility of the expected and data going out of sync.

## 5. pyarrow: casting strings to time32

### Attempt
Generated time-of-day strings (`"07:00:00"`) in a pandas DataFrame and tried casting the column to `pa.time32("ms")`:
```python
table = pa.Table.from_pandas(df)
table = table.cast(date_schema)  # where schema has time32("ms")
```

### Issue
`ArrowNotImplementedError: Unsupported cast from large_string to time32 using function cast_time32`. pyarrow cannot cast string columns directly to time types.

### Fix
Compute milliseconds-since-midnight as integers in Python and pass those directly:
```python
millis_of_day = (seconds_of_day * 1000).astype(np.int32)
time_col = pa.array(millis_of_day.tolist(), type=pa.time32("ms"))
```
`time32("ms")` accepts integers representing milliseconds since midnight.

## 6. Silent Pass: ComparableOps<&str> for Date/DateTime/Time

### Discovery
Running the integration harness with fail columns showed all `gt`, `ge`, `lt`, `le`, `eq`, `between` constraints on Date/DateTime/Time columns passing even when data clearly violated them.

### Root cause
`ComparableOps<&str> for Column` had a catch-all fallback:
```rust
impl ComparableOps<&str> for Column {
    fn gt(&self, compare: &str) -> Vec<Option<bool>> {
        match self {
            Column::Str(col) => col.gt(compare),
            _ => vec![None; self.len()],  // Date, DateTime, Time all fell here
        }
    }
    // same for ge, lt, le, equal, between
}
```
All `None` → no `Some(false)` in the mask → constraint formatter finds no failures → passes.

### Fix
Added `Date`, `DateTime`, `Time` arms to each method — parse the string as the appropriate type, delegate to the typed `ComparableOps` impl:
```rust
Column::Date(col) => NaiveDate::from_str(compare)
    .map_or_else(|_| vec![None; self.len()], |d| col.gt(&d)),
Column::DateTime(col) => NaiveDateTime::from_str(compare)
    .map_or_else(|_| vec![None; self.len()], |d| col.gt(&d)),
Column::Time(col) => NaiveTime::from_str(compare)
    .map_or_else(|_| vec![None; self.len()], |d| col.gt(&d)),
```
`between` matches on a tuple of two parse results:
```rust
Column::Date(col) => match (NaiveDate::from_str(lower), NaiveDate::from_str(upper)) {
    (Ok(lo), Ok(hi)) => col.between(&lo, &hi),
    _ => vec![None; self.len()],
},
```

### Second bug: unreachable! panic
Once the comparisons actually returned `Some(false)`, the failed value formatter in `check_greater_than_str` (and all five siblings) hit:
```rust
_ => unreachable!("gt(str) on non-str column"),
```
This was safe before because `None` meant no failures reached the formatter. Now Date/DateTime/Time values do fail, so this `unreachable!` panics. Added arms for each type using the inverse conversion functions to format values for display:
```rust
Column::Date(col) => (
    idx,
    col.0[idx]
        .map(|val| i32_to_naive_date(val).map_or("null".to_string(), |d| d.to_string()))
        .unwrap_or_else(|| "null".to_string()),
),
// same pattern for DateTime and Time
```

## 7. Silent Pass: is_in for Date/DateTime/Time

### Discovery
Integration harness showed `is_in` constraints on Date/DateTime/Time columns always passing — even a value clearly not in the set.

### Root cause — two levels
**Level 1: `parse_is_in` in main.rs**
Saw string values like `"2021-03-01"` and created `ValuesSet::StrSet`. Had no type awareness:
```rust
} else if arr.iter().all(|v| v.as_str().is_some()) {
    Ok(ValuesSet::StrSet(...))
}
```

**Level 2: `Column::is_in`**
Had no arm for `(Date/DateTime/Time, StrSet)`:
```rust
_ => vec![None; self.len()],  // silent pass
```

### Why auto-detecting type from JSON values is wrong
`"2021-03-01"` could be a date string or just a string. If we try parsing as NaiveDate first, then NaiveDateTime, then NaiveTime, the first successful parse wins — but that might not match the actual column type. Ambiguity is unavoidable without knowing the column dtype.

### Fix
Added `col_dtype: &DtypeConfig` parameter to `parse_is_in` and threaded it through `parse_column_constraint`. Branch on dtype to parse strings into the correct internal representation:
```rust
DtypeConfig::Date => {
    let t_arr = arr
        .iter()
        .map(|v| NaiveDate::from_str(v.as_str().unwrap()))
        .collect::<Result<Vec<NaiveDate>, _>>()?;
    let output_arr = t_arr.iter().map(naive_date_to_i32).collect();
    Ok(ValuesSet::Int32Set(output_arr))
}
DtypeConfig::DateTime => { /* same with NaiveDateTime, naive_datetime_to_i64, Int64Set */ }
DtypeConfig::Time => { /* same with NaiveTime, naive_time_to_i64, Int64Set */ }
DtypeConfig::Bool => bail!("is_in is not supported for bool columns"),
```

The two-step approach (collect into `Vec<NaiveX>` first, then map to integers) avoids error type conversion juggling. `collect::<Result<Vec<NaiveDate>, _>>()` uses the chrono error type directly, then `?` propagates it via the `From` impl.

Also fixed the Int/Float/Str branches from `unwrap()` to proper error propagation using `ok_or_else`.

### Ripple: test signatures
`parse_is_in` and `parse_column_constraint` gained a dtype parameter. All existing tests had to be updated to pass a `DtypeConfig` value. Tests that don't use `is_in` pass `DtypeConfig::Int` as a neutral default.

## 8. compare_results.py: constraint name mismatch

### Issue
The CLI emits `"in_set"` as the constraint name in JSON output (from `ColumnConstraint::InSet`'s `Display` impl), but `expected.json` uses `"is_in"` (matching the schema config key). Compare script looked up by constraint name and always returned MISSING for `is_in` entries.

### Fix
Normalize constraint names when building the lookup from CLI output:
```python
def normalize(c):
    return "is_in" if c.startswith("in_set") else c.split("(")[0]
```
